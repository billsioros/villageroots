# Technical Analysis & Architecture Design: VillageRoots

**Stack Constraint:** Next.js (Frontend/API) + Supabase (Auth, Database, Storage, Vector)

## 1. System Architecture Overview

* **Frontend:** Next.js (App Router), React, Tailwind CSS.
* **State Management:** Zustand (for complex canvas state) + React Query (for server state caching).
* **Canvas Rendering:** `react-force-graph` (WebGL/Three.js wrapper for performant 2D/3D physics rendering of thousands of nodes).
* **Rich Text Editor:** `TipTap` (headless wrapper around ProseMirror for the Notion-like sidepanel).
* **Backend / Database:** Supabase (PostgreSQL).
* **AI/Vector Services:** Supabase Edge Functions / Next.js API Routes, `pgvector` (for GraphRAG embeddings), and OpenAI/Gemini APIs (for OCR and LLM).
* **Storage & Auth:** Supabase Storage (for document/photo uploads) and Supabase Auth (RBAC for Admins vs. Users).

## 2. Database Design (Graph in PostgreSQL)

To achieve graph capabilities (Nodes and Edges) in a relational database, we will use an **Adjacency List Model** heavily relying on JSONB for flexibility and standardizing the schema.

### 2.1. Core Tables

**Table: `nodes` (Entities)**
Stores all entities (Persons, Toponyms, Landmarks) in a single polymorphic table to simplify edge relationships.

* `id` (UUID, Primary Key)
* `type` (Enum: 'person', 'family', 'toponym', 'landmark', 'event')
* `label` (String, e.g., Name of the person/place - extracted for fast search)
* `document_content` (JSONB - TipTap editor content)
* `properties` (JSONB - structured data like `birthYear`, `coordinates`, `origin`)
* `status` (Enum: 'pending', 'approved', 'rejected' - for Moderation)
* `privacy` (Enum: 'public', 'private' - for GDPR living/deceased logic)
* `created_by` (UUID, Foreign Key to `auth.users`)
* `created_at`, `updated_at` (Timestamps)

**Table: `edges` (Relationships)**
Stores the directional connections between nodes.

* `id` (UUID, Primary Key)
* `source_id` (UUID, FK to `nodes.id`)
* `target_id` (UUID, FK to `nodes.id`)
* `type` (Enum: 'CHILD_OF', 'OWNS_LAND_AT', 'BUILT_BY', etc.)
* `properties` (JSONB - context like `date_range`, `evidence_notes`)
* `status` (Enum: 'pending', 'approved', 'rejected')
* `created_by` (UUID, FK to `auth.users`)

**Table: `node_embeddings` (For Phase 4 GraphRAG)**

* `id` (UUID, PK)
* `node_id` (UUID, FK to `nodes.id`)
* `embedding` (vector(1536) - pgvector type)
* `content_chunk` (Text - stringified representation of node properties + markdown for AI context)

### 2.2. Database Indexing & Graph Queries

* **Indexes:** B-Tree indexes on `edges(source_id)` and `edges(target_id)` are mandatory for fast graph traversals. GIN indexes on `nodes(properties)` and `nodes(document_content)` for JSON querying.
* **Recursive CTEs:** To fetch a family tree, we will use PostgreSQL `WITH RECURSIVE` queries in Supabase RPC (Remote Procedure Calls) to traverse the `edges` table efficiently without multiple round-trips to the server.

## 3. Security, Privacy & GDPR (Row Level Security - RLS)

Supabase RLS is critical for handling the Moderation Queue and Living vs. Deceased privacy rules at the database level.

* **Moderation Policy:**
* `SELECT` on `nodes` and `edges` where `status = 'approved'`.
* Users can `SELECT` their own pending nodes (`created_by = auth.uid()`).
* Admins (verified via a `user_roles` table or JWT claims) bypass these restrictions.


* **GDPR Privacy Policy:**
* Nodes marked `privacy = 'private'` are stripped of their `document_content` and `properties` at the database level unless the requesting user has explicit permission (e.g., claimed the node). A database view or an Edge Function will map private nodes to return only `id` and a generic label (e.g., "Living Person") to unauthorized clients.

## 4. Phase-by-Phase Technical Implementation Plan

### Phase 1: Infinite Canvas, Manual Nodes, Notion-like Editor

**Goal:** Deliver the core spatial exploration and knowledge-capture UI.

* **Infinite Canvas (`react-force-graph`):**
* Nodes and links are fetched via Supabase PostgREST endpoints.
* The graph payload (Nodes + Edges) is loaded into Zustand state.
* Using the `react-force-graph-2d` (Canvas API) or `react-force-graph-vr` (Three.js) library, nodes are rendered with collision forces (d3-force) to form organic clusters.
* Coordinates generated by the physics engine are stored temporarily in client state; when a user "pins" a node, its `{x, y}` coordinates are patched to the `nodes.properties` JSONB in Supabase.


* **The Sidepanel Editor (`TipTap`):**
* When a node is selected, a Next.js parallel route or a framer-motion animated aside opens.
* TipTap is configured with React. It supports `/` commands (slash menu) for standard markdown elements.
* Data is auto-saved (debounced by 1000ms) to the `nodes.document_content` field in Supabase as a JSON structure, ensuring rich text formatting is preserved.



### Phase 2: External Embedding (Maps/Wikipedia)

**Goal:** Enrich node documents with inline interactive context.

* **TipTap Custom Extensions:**
* We will write a custom TipTap Node Extension called `ExternalEmbed`.
* When a user pastes a URL, a Next.js API route (`/api/parse-embed`) uses an oEmbed library (like `unfurl`) to validate the link.
* If it's a Wikipedia link, the API fetches the summary paragraph and thumbnail.
* If it's a Google Maps link, the extension renders an `<iframe>` within the TipTap document block.
* The resulting widget data is saved seamlessly into the TipTap JSON tree in Supabase.



### Phase 3: OCR / AI-Assisted Form Prefilling

**Goal:** Digitize handwritten archives automatically.

* **Upload Pipeline:**
1. User uploads a photo of an old document in the UI.
2. Frontend uploads the file to **Supabase Storage** bucket (`archive-scans`).


* **AI Extraction (Supabase Edge Functions):**
1. An Edge Function (`process-ocr`) is triggered (or called via Next.js API).
2. The function retrieves the secure URL of the image and sends it to a Vision LLM (e.g., OpenAI `gpt-4o` or Gemini `Pro Vision`).
3. **Prompting:** The LLM is instructed with a strict JSON schema via Structured Outputs to return extracted entities (Names, Dates, Places) and their implied relationships.
4. **Client Handoff:** The Edge Function returns this JSON payload to the Next.js frontend.


* **UI Resolution:**
* The frontend renders a "Review Extracted Data" modal.
* The user sees a side-by-side view: original image vs. extracted nodes/edges.
* Upon confirmation, the UI executes bulk `INSERT` statements to the `nodes` and `edges` tables (with `status = 'pending'`).


* **Storage cleanup (PTDN-36):**
* Uploads die with their request, so orphaned scans are purged by a scheduled sweep.
* Mechanism: a pg_cron job (via `pg_net`) POSTs daily at 04:00 UTC to the
  `archive-scan-cleanup` Edge Function, which deletes `archive-scans` objects older
  than 24h (TTL) using the Storage Admin API. Supabase Storage has no native
  lifecycle rules, so this scheduled sweep is the supported expiry mechanism.
* The sweep only ever touches objects older than 24h — an OCR request lasts minutes
  (`REQUEST_TIMEOUT_MS`), so legitimate in-flight scans are never at risk.
* Config lives in `supabase/migrations/0012_archive_scan_cleanup.sql`:
  idempotent helpers `public.vr_archive_scan_cleanup_schedule(function_url, apikey,
  cleanup_secret)` / `public.vr_archive_scan_cleanup_unschedule()` register/remove the
  job and are run once per environment (URL differs local vs prod; see migration comment).
* Deploy: `supabase functions deploy archive-scan-cleanup --no-verify-jwt`, then
  `supabase secrets set CRON_SECRET=...` (the handler gates on the `x-cleanup-secret`
  header).


### Phase 4: GraphRAG & Linkage Prediction

**Goal:** Introduce conversational querying and AI graph expansion.

* **GraphRAG Implementation:**
1. **Ingestion Trigger:** Whenever an approved node is created or its TipTap document is updated, a Supabase Database Webhook triggers an Edge Function.
2. **Embedding:** The function compiles the node's properties, label, and raw text from the TipTap JSON, sends it to an embedding model (e.g., `text-embedding-3-small`), and stores the vector in the `node_embeddings` table using `pgvector`.
3. **Querying:** When a user asks a question in the UI, a Next.js API route generates an embedding of the question.
4. **Hybrid Search:** Supabase performs a vector similarity search (`<->` operator in pgvector) to find the top 5 most relevant nodes.
5. **Graph Traversal (The "Graph" in GraphRAG):** For those 5 nodes, a recursive CTE grabs their direct neighbors (edges 1-hop away).
6. **LLM Synthesis:** The original nodes + their neighbor context + the user prompt are sent to the LLM to generate the final conversational answer. The frontend highlights the retrieved nodes on the 2D canvas.


* **Linkage Prediction (Heuristic + LLM):**
* A cron-triggered Supabase Edge Function runs nightly over unlinked nodes.
* It uses a combination of PostGIS/location data (if nodes have coordinates), timeline overlaps, and naming conventions.
* Potential matches are written to a new table `edge_predictions` (`source_id`, `target_id`, `confidence_score`, `reason`).
* The frontend pulls from this table to render "dashed, glowing lines" on the canvas. Clicking the line opens a UI prompt to "Accept Connection", which upgrades the prediction into a hard edge in the `edges` table.
